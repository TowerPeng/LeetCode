ThreadLocal的理解
ThreadLocal是java中的一个工具类，用于创建线程本地变量。每个线程在访问这个变量时都会有自己独立的副本，因此变量之间互不干扰。
在多线程编程中，共享变量需要考虑线程安全性及隔离性。它使用Thread对象作为key，在内部数据结构中查找对应的变量副本。
用法：
线程上下文管理，存储用户的信息，比如token解析的用户信息
用户会话管理，在web应用中，可以存储用户的会话信息
需要注意以下几点：
1、内存泄漏：在使用完ThreadLocal对象后，必须调用remove方法清理与当前线程相关的副本变量，否则，这些变量将无法被垃圾回收机制回收，从而导致内存泄漏。（弱引用）
2、线程安全性：ThreadLocal对象本身是线程安全的，但是，如果多个线程同时访问同一个ThreadLocal对象，可能会导致数据不一致。
3、数据隔离性：ThreadLocal适用于多线程环境下需要保持变量独立的场景，可以避免使用传统的同步方式对共享变量进行操作，提高并发性能。

InheritableThreadLocal可以用于继承父线程的变量，比如在父线程中设置用户信息，子线程中可以获取到用户信息。
缺点：
1、线程复用问题，线程池的线程是复用的，并不是每次任务都新建，当一个线程执行完任务后，InheritableThreadLocal值可能会传递，导致上下文污染。
2、只支持创建时继承，无法动态继承。
3、仅单向传递，不能从子线程传递至父线程，也无法跨线程传递。
TransmittableThreadLocal（阿里的ttl框架）
扩展InheritableThreadLocal，并增加了传递能力，线程池友好，即使线程复用，也能保证每次提交的是提交的上下文，任务间互不干扰。
支持动态传递，可以在父线程随时修改TTL值，后续提交的任务会捕获新值。
总结
如果只是简单的父子线程传值（不涉及线程池），InheritableThreadLocal 足够。
一旦涉及线程池、异步任务等线程复用场景，必须使用 TransmittableThreadLocal 来保证上下文正确传递。


CountDownLatch 和 CyclicBarrier 是 Java 并发包（java.util.concurrent）中提供的两个同步辅助类，用于协调多个线程之间的协作。它们都能让线程等待，但设计目的和行为有显著区别。
CountDownLatch：
初始化时设定一个计数器（正数）。一个或多个线程调用 await() 阻塞自己，直到其他线程调用 countDown() 将计数器减至 0，被阻塞的线程才会被唤醒。
计数器是一次性的，归零后无法再使用。
countDown() 可以在任意线程调用，不要求是同一个线程。
常用于“等待事件发生”的场景，比如主线程等待所有子线程加载完数据。
CyclicBarrier：
初始化时设定一个“屏障数”（参与线程的个数）。每个线程到达屏障点时调用 await() 进入等待，直到所有线程都调用了 await()，屏障才会打开，所有线程同时继续执行。
计数器可以重复使用，所有线程释放后，屏障自动重置。
支持一个可选的 Runnable 参数，当最后一个线程到达时，该任务会在所有线程被释放之前执行。
常用于“分阶段计算”，比如并行处理数据，每完成一个阶段需要同步结果。

死锁问题：
java中，死锁是一种阻塞现象，发生在两个或者多个线程相互持有对方所需的资源，从而导致线程无法继续执行的情况。当线程陷入死锁状态，就无法释放他们持有的资源。
死锁的四个条件：
1、互斥条件：资源不能被多个线程共享
2、持有和等待：线程已经持有至少一个资源并等待获取另外的资源。
3、不剥夺条件：资源不能持有它的线程中剥夺，必须由线程自行释放。
4、循环等待条件：存在一个线程循环等待链，链中的每个线程都等待下一个线程持有的资源。

线程池核心参数：
1、corePoolSize：核心线程数，默认情况下，线程池会创建corePoolSize个线程，即使没有任务可执行。
2、maximumPoolSize：最大线程数，线程池允许创建的最大线程数。
3、keepAliveTime：线程空闲时间，当线程数大于corePoolSize时，多余的空闲线程在空闲时间后被销毁。
4、unit：keepAliveTime的单位。
5、workQueue：任务队列，用于存放等待执行的任务。
6、threadFactory：线程工厂，用于创建新的线程。
7、rejectedExecutionHandler：拒绝策略，当任务队列已满且线程数达到maximumPoolSize时，线程池会拒绝新任务。
