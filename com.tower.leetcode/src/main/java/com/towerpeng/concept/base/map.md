HashMap的底层结构：
在jdk1.7以前，HashMap的底层结构是一个数组+链表，数组的默认大小为16，当数组的元素个数达到数组的容量的0.75的时候，就会扩容，扩容之后，数组的容量变为原来的2倍。
在jdk1.8以后，HashMap的底层结构是一个数组+链表+红黑树，当链表长度大于8并且hash桶（元素）的容量大于64的时候，链表就会转换成红黑树。
jdk1.7以前是头插法，新来的节点插在链表头部，会造成死循环
jdk1.8以后是尾插法，新来的节点插在链表尾部，解决了死循环问题
jdk称为entry，jdk称为node

为什么创建HashMap时最好指定初始容量？原因是什么？为什么不直接new HashMap()？
在创建 HashMap 时最好指定初始容量，主要是为了优化性能，减少扩容次数。
如果不指定，HashMap 会使用默认的初始容量（16），当插入的元素数量超过阈值（容量 × 负载因子）时，就会触发扩容操作。扩容需要重新计算所有已有元素的哈希值并重新分配存储位置，这个过程比较耗时。如果能预估元素数量并合理设置初始容量，可以避免或显著减少扩容，提升程序效率。
直接使用无参构造会得到默认容量16，如果存储的元素数量不多（比如少于12），则没有问题；但如果存储数量较多，就会导致不必要的扩容，影响性能。因此，在能预估数据规模的情况下，显式指定初始容量是一个良好的编程习惯，可以避免运行时性能损耗。

HashTable和ConcurrentHashMap的区别
1、锁的粒度不同，HashTable是全局大锁，在get和put方法上加了Synchronized，ConcurrentHashMap是局部小锁，分段锁，jdk1.8中，它使用CAS+Synchronized锁住哈希桶的头节点。只有两个线程同时操作同一个元素才会竞争，大大提高了并发吞吐量。
2、性能差距，高并发环境下HashTable性能会急速下降，线程会争抢锁，ConcurrentHashMap性能会提高很多，性能接近HashMap。
3、都不允许null作为key和value
