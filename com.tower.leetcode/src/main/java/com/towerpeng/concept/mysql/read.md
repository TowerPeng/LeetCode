MYSQL索引底层结构：B+树
1、快速查找，B+树是平衡多路二叉树，树的高度相对较低，能够快速定位到目标数据，在大数据量的情况下，B+树的查找效率更高
2、有序性，B+树的特点是节点上的键值是有序排列的，这使得范围查询，排序和分组操作中效率更高，对于mysql的查询操作常常涉及到范围查找，B+树能有效支持。
3、支持高效的插入和删除操作，B+树的平衡特性使得插入和删除操作相对简单，不需要进行大量的数据迁移，B+树叶子节点之间使用双向链表控制，可以快速定位插入或删除的位置。
4、适应磁盘存储：mysql通常要将数据存储在硬盘上，而不是内存中，B+树的节点大小被控制在硬盘页面大小的范围内，使得每次读取数据量最大化，减少IO操作。
5、支持有序存储和范围查找，B+树能够支持有序存储和范围查找，使得mysql的索引性能更高。

MVCC是多版本并发控制，Multi-Version Concurrency Control ，是一种数据库的并发控制机制，目标是保证数据一致性和隔离性的同时，提供更好的并发性能。
MVCC的原理：
1、每行数据都有多个版本：每行数据都有多个版本，每当对数据进行更新操作，不会覆盖原来的操作，而是生成新的版本，每个版本都有一个时间戳，用于标识该版本的创建时间。
2、读操作只读取符合时间条件版本，在读取数据时，事务只能看到创建时间早于事务开始时间的版本。这样可以保证事务读取的数据是一致的，不影响其他事务。
3、写操作保存多个版本：当进行写操作时，会生成新版本并更新到数据行中，旧的版本仍然存在，不会被删除，这样可以保证数据一致性。
4、版本控制：为了维护数据的一致性和隔离性，mvcc使用了版本控制，在事务执行过程中，只能读取到版本号小于等于事务开始的版本，这样可以保证读取的数据在事务开始时是一致的
5、垃圾回收，为了防止旧版本无限增加，增加数据库的存储空间，mvcc采用了垃圾回收机制，当一个事务提交时，系统会检查该事务产生的版本是否有其他事务使用，如果没有，该版本会被删除，释放空间。

MVCC 的核心思想是：当多个事务同时操作同一数据时，每个事务看到的都是数据在特定时间点的快照（版本）。写操作会创建新版本，而读操作可以读取旧版本，从而避免加锁带来的等待。
InnoDB（MySQL 的常用存储引擎）是 MVCC 的典型实现。
在 MySQL 的 InnoDB 存储引擎中，读已提交（READ COMMITTED）和可重复读（REPEATABLE READ）这两个隔离级别主要依靠 MVCC 来实现一致性非锁定读（快照读）。
另外两个级别（读未提交、串行化）则基本不依赖 MVCC 或通过加锁实现。

事务的隔离级别：
1、读未提交Read-uncommitted，最低的隔离级别，事务可以读到未提交的数据，可能出现脏读，幻读，不可重复读
2、读已提交Read-committed，事务可以读到已提交的数据，但是同一事务中，多次读取同一行数据可能出现不一致的情况，可能会出现幻读，不可重复读
3、可重复读Read-Repeatable，在同一个事务内多次读取到同一行的数据始终保持一致。MYSQL的默认隔离级别就是可重复读，通过MVCC机制来实现，在读取操作期间不会看到其他事务的修改，有效的解决了不可重复读的问题
4、串行化Serialzable，串行化是最高级别，串行化执行可以避免脏读，幻读，不可重复读，但是并发性能较差，导致大量锁竞争和资源争抢。

索引失效的场景：
1、使用左模糊匹配或者左右模糊匹配，导致索引失效，引发全表扫描，%xx，或者%xx%，
2、对索引字段使用函数，mysql8以后引入了函数索引，可以利用函数索引
3、查询条件进行表达式计算，索引保存的是原始值，而查询条件是计算后的值，
4、对索引字段进行隐式转换，如字符串类型的电话号码，查询用整型，
5、没有符合最左匹配原则
6、索引列可为NULL，is not null可能导致索引失效
7、使用or，not in等，无法确定范围
8、字段选择太低，比如某个字段大部分为固定值，全表扫描比索引更快

redoLog，binlog，undolog
1、redoLog，保证事务的持久性（Durability），即一旦事务提交，数据就不会丢失。
2、binLog，数据恢复和主从复制。它是 MySQL 实现数据备份、增量恢复和主从同步的基础。
3、undoLog，用于数据库事务回滚，保证事务的原子性（Atomicity），同时支持 MVCC（多版本并发控制）。

InnoDb和MyIsam的区别
事务支持：InnoDb支持完整的 ACID 事务，有提交、回滚和崩溃恢复能力 ，MyIsam不支持事务
锁粒度：InnoDB 是行锁，MyISAM 是表锁
索引结构：InnoDB 使用 聚簇索引。数据文件本身就是索引文件（.ibd），主键索引的叶子节点直接存储整行数据，查询速度极快。MyISAM 使用 非聚簇索引。索引和数据分离，索引文件（.MYI）的叶子节点存储的是指向数据文件（.MYD）的指针。
外键支持:InnoDb支持外键约束，能保证数据的参照完整性，MyIsam 不支持外键。
并发性能：InnoDB并发性能高，支持 MVCC（多版本并发控制），MyIsam并发性能较低，不支持 MVCC。
崩溃恢复：InnoDB 具备自动崩溃恢复能力。通过 redo log 和 undo log 保证数据不丢失或快速恢复，MyIsam 崩溃后数据易损坏，需要手动修复（REPAIR TABLE 或 myisamchk）。

mysql查询执行过程：
1、连接器：负责与客户端建立连接，获取权限，维持和管理连接
2、查询缓存：mysql8.0以前会查询缓存
3、分析器：词法分析，语法分析，识别字符串分别代表什么，是否满足语法
4、预处理器：进一步检查表名，列表是否存在，解析名字和别名，是否有歧义
5、优化器：当有多个索引可用，决定用哪个索引
6、执行器：执行SQL语句，返回结果给客户端

SQL怎么优化：
避免使用select *，会回表，浪费cpu和内存资源
小表驱动大表，减少计算量，提高查询效率
用连接查询代替子查询，利用数据库索引，提高查询性能
提升group by效率，缩小数据范围，减少子查询，添加合适索引
批量操作，减少与数据库的交互次数提升性能
使用limit提高查询效率，优化分页，简化查询结果
用union all代替union，更快的查询，更精准的结果
join表不应过多

分库分表下怎么分页问题解决方案：
1、es，将分页查询迁移到es，适用于复杂的查询和分页场景
2、ShardingSphere，ShardingSphere提供了一些内置的分页优化：自动改写SQL+全局查找法+流式处理（排序，过滤）
3、业务妥协方案：只查询当前分片的数据，提示用户“仅显示部分结果”

不用工具，怎么处理分库分表的分页问题？
全局查找法：查出数据，然后再合并排序分页，如按2取模，limit2，2，需要同时查询0，4数据，如果数据只在一个节点时，需要查0到4，（0，2+offset）
问题：翻页越深，性能越差
方案：禁止跳表法，拿到上一页的最大id作为过滤条件，这样就不需要从0开始
select * from t_order where id > 上一页maxID order by id limit 10

主从延迟解决方案：
1、MYSQL5.7以后，可以开启并行复制功能，从库多线程并发复制（slave_parallel_workers = 8~16）cpu的两倍，io密集型，充分利用磁盘吞吐
开启并行复制只是能减少概率，但还是会发生延迟，比如长事务阻塞，批量更新或者主库瞬间tps远超同步的并行复制线程数量，或者主库的性能比从库性能更好，还是会出现主从延迟的情况，所以可以加兜底，强制读主库
2、关键功能读主库，其他非关键功能读从库
3、redis标记法，设置时间过期（需判断主从延迟时间），如设置2秒，redis有数据主动查主库，否则查从库
