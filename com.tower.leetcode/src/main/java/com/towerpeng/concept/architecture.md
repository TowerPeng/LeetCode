一、项目背景与业务挑战
聚玩平台 是网鱼网咖旗下综合性娱乐平台，整合电竞、酒店、会员、赛事、积分抽奖等业务，覆盖 PC 桌面、小程序、APP 等多端，日活 20 万以上，与 PUBG、腾讯等深度合作。
鱼助手3.0 是其核心载体，为玩家提供一站式服务；同时推进海外系统（新加坡、日本、香港）及自研 鱼灵AI 智能问答系统。
核心业务难点
多端统一，业务复杂：PC、小程序、APP 三端业务逻辑相似但交互形态不同，需复用核心能力。
高并发与秒杀场景：积分抽奖、赛事秒杀等活动瞬间流量激增，需保障系统稳定性与数据一致性。
数据体量大且迁移复杂：3000 万用户账户迁移，8000 万条用户操作日志合并，要求零停服、零数据丢失。
多部门中台协同：对接会员中台、券中心、商品中台、支付中台等，需要设计清晰的边界与交互协议。
国际化多地域部署：新加坡、日本、香港业务需解决合规、网络延迟、数据隔离等问题。
AI 能力快速落地：需构建 RAG 智能问答，支撑公司内部知识库，同时保持可扩展性。
二、微服务拆分的设计思路
1. 拆分原则：领域驱动 + 中台化
我们遵循 DDD（领域驱动设计） 划分业务边界，同时借鉴中台思想将通用能力下沉为独立服务：
会员中台：统一管理用户身份、登录态、会员等级、积分账户。
理由：会员是跨业务的核心资产，独立后可供聚玩、鱼助手、海外版等多个前端复用，避免重复建设。
券中心：独立负责优惠券的生成、发放、核销、过期处理。
理由：券是营销活动的核心资产，抽奖、签到、赛事奖励都依赖它，独立后便于统一配置、监控和审计。
商品中台：管理电竞酒店房型、商品 SKU、库存、价格。
理由：商品信息复杂且变动频繁，需要独立维护，同时为后续扩展其他售卖场景（如周边商城）奠定基础。
支付中台：统一对接支付宝、微信等支付渠道，封装订单创建、退款、回调处理。
理由：支付链路安全敏感，集中管理可降低各业务线对接成本，确保资金安全。
活动中心：负责抽奖、签到、任务、赛事等营销活动配置与执行。
理由：活动逻辑多变，单独服务便于快速迭代，同时可利用其独立的高并发处理能力。
消息中心：负责推送、短信、站内信、长连接（MQTT）消息。
理由：消息通道与业务解耦，便于统一管理推送策略和模板。
AI 服务（鱼灵AI）：独立提供文档解析、向量化、检索增强、LLM 调用能力。
理由：AI 业务迭代快，单独部署可避免影响主链路，也便于未来升级模型或切换供应商。
2. 拆分后的服务治理
服务注册与发现：采用 Nacos，因其支持 AP 模式（可用性优先），适合内网高频注册场景，且与 Spring Cloud Alibaba 生态无缝集成。
配置中心：同样使用 Nacos，实现配置动态刷新，避免重启。
API 网关：Spring Cloud Gateway，基于 WebFlux 非阻塞模型，承担路由、鉴权、限流、日志等横切关注点。选择 Gateway 是因为其性能优于 Zuul 1.x，且与 Spring Cloud 生态一致。
三、关键技术难点与设计决策
1. 高并发抽奖/秒杀系统
难点：瞬间流量可达到平时数十倍，需保证库存扣减准确、不超发、不重复发放奖品，同时用户体验流畅。
设计：
前端限流：通过 CDN 和 Nginx 限制请求频率。
网关层限流：Gateway 集成 Sentinel，针对抽奖接口设置 QPS 阈值，超出快速失败。
库存预热：抽奖活动开始前，将奖品库存预加载到 Redis，使用 Lua 脚本 原子扣减。
异步发券：扣减成功后，发送 RocketMQ 消息，由券中心异步生成优惠券。
理由：发券涉及数据库写入、跨服务调用，同步操作会拖慢接口响应；消息队列削峰填谷，同时保证最终一致性。
防重复提交：使用 Redisson 分布式锁，基于用户 ID + 活动 ID 生成锁 Key，防止同一用户并发抽奖。
为什么用 RocketMQ？
相比 Kafka，RocketMQ 在金融级消息可靠性、事务消息、延时消息上有更丰富的特性，且与阿里云生态集成好（公司已使用阿里云全套服务）。同时支持 Tag 过滤，便于消费端按业务分发。
2. 3000 万用户账户迁移 + 8000 万日志合并
难点：历史系统与新建系统并存，需平滑迁移，业务不能停服；数据一致性要求高，迁移后需可追溯、可回滚。
设计：
双写方案：迁移期间，新数据同时写入新旧两个系统，确保两边数据同步。
理由：允许随时切流，若新系统出现问题可快速回滚。
分批迁移：按用户 ID 分片，每批迁移一定数量用户，利用 XXL-JOB 调度，并记录迁移进度。
数据校验：迁移完成后，通过离线任务对比新旧系统关键字段（账户余额、会员等级、积分等），差异项自动重试或人工介入。
日志合并：用户操作日志量巨大，使用 Spark 作业 清洗、去重后写入新系统的日志存储（阿里云 SLS），并建立索引。
为什么用 XXL-JOB？
分布式定时任务调度，支持分片、失败重试、任务监控，比 Quartz 更适合大规模数据迁移场景。
3. 多部门中台协同的复杂业务闭环
难点：业务链路长，涉及会员、券、商品、支付等多个中台，任何一个环节失败都需妥善处理，避免数据不一致。
设计：
编排层：在业务服务（如活动中心）中通过 CompletableFuture 异步编排多个中台调用，并设置超时与降级策略。
理由：提升吞吐量，避免串行调用累积延迟。
分布式事务：采用 TCC 模式 或 本地消息表 + RocketMQ 保证最终一致性。
例如：用户参与抽奖消耗积分，先扣减积分（预留资源），成功后再发放优惠券；若发券失败，通过事务消息回滚积分。
可观测性：所有跨服务调用注入 Trace ID，通过阿里云 SLS 实现全链路追踪，便于排查分布式问题。
4. 国际化多地域部署
难点：海外机房网络延迟高，需满足各地数据合规（如 GDPR），同时保持国内统一管理。
设计：
多地域部署：在新加坡、日本、香港各部署一套独立的微服务集群，数据库物理隔离，满足数据本地化要求。
数据同步：仅同步必要的配置数据和基础数据（如商品信息），通过 Canal 监听 MySQL binlog 同步到海外。
域名与流量：使用云厂商的全局负载均衡（如阿里云 DNS 智能解析）根据用户地理位置解析到最近机房。
API 版本化：海外版与国内版共用同一套服务代码，通过配置中心区分环境，使用 Apollo 管理不同环境配置。
5. AI 智能问答系统（鱼灵 AI）
难点：企业内部文档格式多样（Word、PDF、Markdown），需要准确检索并生成回答，同时保证低延迟。
设计：
RAG 架构：采用 LangChain4j 搭建，核心流程：
文档切分：按段落、标题切分，保持语义完整性。
向量化：使用通义千问 embedding 模型，将文本转为向量，存入 Milvus。
检索增强：用户问题向量化后，从 Milvus 检索最相似的 Top-K 片段，组合成 Prompt 送入大模型。
为什么选 Milvus：Milvus 是专门为向量检索设计的开源数据库，支持十亿级向量毫秒级检索，且与云原生生态（K8s）集成好。
大模型选型：初期使用通义千问 API，快速验证效果；后续支持私有化部署 DeepSeek 或 Ollama，兼顾成本与数据安全。
MCP 服务对接：通过 Model Context Protocol 接入外部工具（如天气、地图），增强 AI 能力边界。
四、技术选型总结
技术领域	选型	理由
微服务框架	Spring Cloud Alibaba	国内生态成熟，与阿里云产品集成好，Nacos 兼具注册与配置
容器编排	Kubernetes (K8s)	全量容器化部署，便于弹性伸缩、滚动更新、多环境隔离
消息队列	RocketMQ	高吞吐、低延迟，支持事务消息、延迟消息，适合金融级场景
缓存	Redis + Redisson	Redis 高性能，Redisson 提供丰富分布式锁、集合操作
数据库	MySQL 分库分表 + MongoDB	MySQL 存核心业务，分库分表支撑海量数据；MongoDB 存日志、评论等半结构化数据
向量数据库	Milvus	专为 AI 检索设计，高性能、易扩展
日志与监控	阿里云 SLS + Prometheus	SLS 统一日志存储与检索，Prometheus 监控指标
CI/CD	Jenkins + GitLab + Maven	自建流水线，保证代码质量和部署自动化
AI 框架	Spring AI / LangChain4j	与现有 Java 技术栈无缝集成，降低学习成本
五、总结
在网鱼科技的项目中，我们面对的业务复杂度和技术挑战促使我们采用 微服务 + 中台化 架构，通过合理拆分、异步解耦、分布式事务、多地域部署等手段，既支撑了高并发业务，又保证了系统的可扩展性和可维护性。
核心技术决策均基于业务驱动：例如选择 RocketMQ 而非 Kafka 是因为需要事务消息和延时消息；选择 Milvus 是因为向量检索性能要求；选择 Nacos 是因为与 Spring Cloud Alibaba 生态契合且运维简单。

这些经验也为后续的 AI 能力探索和海外业务拓展奠定了坚实基础。


“分布式系统的高可用，核心是冗余 + 自动故障转移。我们在接入层用 DNS 多 IP 和 VIP；应用层做无状态设计 + 负载均衡 + K8s 自愈；服务调用层使用注册发现、熔断重试；
数据层采用主从复制、哨兵或 Raft 共识算法；全局架构上尽量做到多活或至少同城双活。同时配套完善的监控告警和定期混沌演练，确保系统在真实故障时能快速自动恢复，达到 99.99% 以上的可用性。”
