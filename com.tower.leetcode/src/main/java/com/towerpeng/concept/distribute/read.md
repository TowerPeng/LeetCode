
XA:强一致性，性能低，业务入侵低，适用传统金融，低并发，短事务
TCC：最终一致性，性能高，业务入侵高，核心交易，高并发，需自定义锁
本地消息表：最终一致性，性能高，业务入侵种，异步可靠，跨系统非核心数据
RocketMQ 事务消息：最终一致性，性能高，业务入侵低，依赖 RocketMQ，异步确保
Saga：最终一致性，性能高，业务入侵中高，长事务，流程复杂，需补偿

一般建议：
若并发不高且要求强一致，可选 Seata AT 模式（简化版 2PC）或 XA。
若核心交易链路，建议 TCC 或 Saga（通过 Seata 实现）。
若业务允许短暂不一致，优先使用事务消息（RocketMQ）或本地消息表，性能最佳。

Zookeeper设计分布式锁
主要思路是利用zookeeper的临时顺序节点唯一性和顺序性的特点来实现。
1、创建一个Zookeeper节点作为锁的根节点，例如/locks
2、当一个线程获取锁时，它在锁的根节点下创建一个临时顺序节点，例如/locks/lock-0001,并且尝试获取锁
3、线程获取锁的过程是通过检查它的节点是否是锁下面的最小节点，如果是，则表示该线程获得了锁，否则线程监听它创建节点的前一个节点，等待上个节点释放
4、当线程释放锁时，它删除自己创建的节点
这种方式实现的分布式锁具有一定可靠性和性能，但需要确保Zookeeper集群的可用性和性能足够好，同时，需要处理连接断开，会话过期等异常情况，以保证分布式锁的正确性。
此外，还可以使用Zookeeper的超时机制来处理死锁问题。


Redis 分布式锁（以 Redisson 为例）
✅ 优点
性能极高：基于内存操作，适合高并发、低延迟场景，如秒杀、缓存更新。
实现简单：利用 SET key value NX PX milliseconds 一条命令即可完成加锁和过期设置，原子性有保障。（SET key value NX EX seconds）
功能丰富：成熟的客户端（如 Redisson）提供了可重入锁、读写锁、红锁（Redlock）、信号量等多种高级特性，开箱即用。
❌ 缺点与潜在风险
锁超时不可控：如果业务执行时间超过锁的过期时间，锁会被自动释放，导致其他线程同时获取到锁（并发安全问题）。虽然可以启动一个“看门狗”线程（如 Redisson 的 Watchdog）来续期，但在 GC 停顿或网络抖动时仍有风险。
主从数据不一致（锁丢失）：在 Redis 主从架构中，如果 Master 宕机，锁数据尚未同步到 Slave，Slave 晋升为 Master 后，新锁可以被其他客户端获取，破坏了互斥性。
时钟跳跃问题：如果 Redis 服务器的系统时间发生跳跃，可能导致锁的过期时间计算错误，提前或推迟释放。

ZooKeeper 分布式锁（以 Curator 为例）
✅ 优点
强一致性保证：ZooKeeper 的 ZAB 协议保证了集群中数据的强一致性，只要客户端成功创建了节点，所有服务器都能看到，天然避免了锁丢失问题。
锁自动释放更可靠：锁基于临时节点实现。当客户端宕机或网络分区导致会话超时，ZooKeeper 会自动删除该节点，锁立即释放，无需设置超时时间。
等待机制更高效：客户端通过 Watch 机制监听前一个节点的删除事件，一旦锁释放，ZooKeeper 会主动通知等待的客户端。这比 Redis 客户端自旋轮询（不断尝试获取锁）更高效，且对 ZooKeeper 集群的压力更小。
可重入与公平性：基于临时顺序节点，能天然实现公平锁（按照请求顺序获取锁）。
❌ 缺点
性能相对较低：ZooKeeper 的写操作是强一致性的，涉及磁盘 I/O 和 Leader 选举，QPS 通常只有几千到万级别，远低于 Redis 的十万甚至百万级。不适合极高并发、锁粒度极细的场景。
“羊群效应”：如果使用不当（如大量客户端监听同一个节点），释放锁时会惊动大量客户端，瞬间压力巨大。不过 Curator 等客户端已经通过监听前一个节点的机制优化了这个问题。
实现相对复杂：原生 API 较难用，通常需要借助 Curator 等封装好的客户端，引入了额外的依赖。
会话超时与网络抖动：如果发生长时间的“Stop-The-World” GC 或网络抖动，可能导致 ZooKeeper 会话超时，锁被自动释放，但业务其实还在执行，同样可能造成并发问题。不过，相比 Redis 的锁超时，ZooKeeper 的会话超时通常可配置且更可控。
