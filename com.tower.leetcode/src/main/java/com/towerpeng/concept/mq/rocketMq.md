RocketMq是什么？
RocketMq是一款开源的分布式消息中间件，最初由阿里巴巴开发，后来捐赠给Apache软件基金会并成为顶级项目。
它主要用于分布式系统中进行消息传递，帮助实现应用的解耦、流量削峰、异步处理等场景。
简单来说，RocketMQ 就像一个“邮局”：生产者（Producer）把消息（信件）发给消息队列（邮局），消费者（Consumer）再从队列里取走消息进行处理。这样，即使生产者或消费者暂时不可用，消息也不会丢失，系统间的依赖也大大降低。

消息不丢：
生产者发送端：同步发送+重试机制，确保消息从应用成功发出，并收到Broker的确认。
事务消息，解决本地事务与消息发送的一致性问题，从源头避免丢失。
Broker端：同步刷盘，持久化存储，确保消息写入物理磁盘后再返回确认，防止因宕机导致内存数据丢失。
高可用复制，主节点将消息同步复制到从节点后才返回确认，主节点故障时消息不丢。
消费端：手动ACK (消费成功后返回 CONSUME_SUCCESS)，确保业务逻辑处理完成后再确认消息，防止处理中异常导致消息丢失。
消费重试和死信队列，消费失败后按策略重试（最多16次），超过次数进入死信队列，提供人工补偿机会。

重复消费问题：
核心：幂等，同一条消息被消费多次与消费一次的结果完全相同。
RocketMQ 提供了基础支持，但具体去重逻辑需要业务层实现 。
业务处理，如订单id+订单状态判断，如果非指定状态，直接过滤。
分布式锁，对同一消息id加锁，成功则处理，失败则说明已在处理或已处理完，直接跳过。
乐观锁，版本控制，业务数据新增version字段，如果是指定版本号才进行更新。

顺序消费：
生产者端：使用MessageQueueSelector按业务ID（订单id）路有消息，确保同一业务消息进入同一队列。
消费者端：需注册MessageListenerOrderly监听器，为每个队列分配独立线程，单线程消费，确保队列消息顺序执行。
合理设置队列数量（建议4-16个），平衡顺序性和吞吐量需求
实现消费逻辑的幂等性，防止消费失败导致的消费队列阻塞。

消息积压：
大部分消息积压问题出现在消费端，
首先确认有没有慢SQL、异常，定位错误原因，如果异常会导致消息重试，
其次优化处理逻辑，避免消息处理时间过长，如调用三方返回过慢，逻辑改造，如异步，
如果以上还解决不了，开启批量消费，增加消费实例。

整体架构：
生产者集群发送消息到broker集群，消费者集群从broker集群拉取消息，broker集群上报信息到NameServer集群维持心跳。
broker可以理解为RocketMq本身负责接收生产者消息，持久到磁盘，处理消费者的拉取请求。
NameServer本质上是一个轻量级的注册中心，用来管理broker集群、管理topic等，和kafka的zk和kraft差不多。
broker通过topic分类，生产者把不同类型的消息发送给对应的topic，消费者订阅topic，然后进行消费，topic实际上就是逻辑上分类的概念，从存储角度看，topic内部是多个队列，这个队列在kafka叫partition，本质是一样的

一条消息可以被多个消费者消费，怎么知道每个消费者消费到哪？
队列中每个消息都会分配一个唯一标识，叫偏移量，也就是offSet，一个单调递增的整数。所以记录offset就能知道消费到哪了
以上是kafka和rocketmq共有的，rocketMq还有个tag，tag就是同一个topic下对消息更细粒度的分类，可以根据tag去过滤消息，

如果一个topic对应的队列都放在一个机器上，机器的IO就会成为这个topic的性能瓶颈，怎么解决
一个topic下有多个队列，每个队列只存一部分数据，broker是做集群的，一个topic点下的不同队列可以分不到不同的broker节点上，解决了单机性能瓶颈
rocketMq只能保证一个队列的消息是有序的，不同的队列间的消息顺序性无法保证，这是跟kafka是一样的。

如果broker挂了，队列数据丢失了，怎么解决，高可用实现：
rocketMq的高可用和kafka的多副本机制是类似的，kafka多副本本质是对partition去做多副本，rocketMq实际上是对broker做主从，对broker做副本，主节点负责读写请求，从节点负责同步主节点的数据，主节点挂了，就需要在从节点选一个转为主节点，然后处理读写请求。

怎么知道生产者发送消息是到哪个broker上？消费者怎么知道从哪个broker消费消息？
1、注册中心管理broker集群，保存集群状态信息，通过broker定时上报心跳，感知这节点的上下限
2、掌控消息路有，让生产者知道消息应该发送给哪个broker，消费者知道从哪个broker消费消息
3、负责集群的负载均衡和故障转移，保证服务高可用，nameserver也是做集群的

多个消费者组成消费者组，一个消费者组可以并行消费一个topic的多个队列，topic中的一个队列只能被一个消费者组的一个消费者消费，消费者数量超过了队列数量，多余的消费者空闲，就不能消费了。

工作流程：
broker集群定时的去向NameServer发送一个心跳包，上报topic和队列的信息，然后nameServer会在内存中维护一张路有表，记录了topic到broker集群的映射关系，以及每个broker上的消息队列的详细配置，生产者通过访问NameServer就能获取到消息的路有信息，然后发送给对应的broker，
broker接到消息后会持久化到磁盘，然后同步数据给从节点，消息的消费者通过访问这个NameServer就能获取到订阅的topic的路有信息，就知道从哪个broker去拉取消息
